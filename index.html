A1Overview

A job search agent that collects openings directly from company applicant tracking systems, filters them with deterministic rules, scores the rest in one schema-validated Claude call, and texts the best match each morning. One-word replies return the right resume, a tailored one-page PDF, or the next match, and Gmail replies keep every application up to date.

7
applicant tracking systems read directly
1
model call per posting, schema checked
7
nights a new ranker must win before it takes over

A2The problem

Job boards duplicate postings, keep expired listings live, and mix senior roles into entry-level results. Classifying every posting with a language model would spend most of the budget on postings that basic rules can reject.

Finding the role is only half the work. Each application needs the right resume, honest tailoring, and follow-ups, and a silent employer is easy to lose track of.

A3How it works

  1. Weekly: discover companies from Built In NYC, Y Combinator, HN Who is Hiring, SimplifyJobs and VC job boards. Keep companies with 20+ employees or recent verified funding.
  2. Every weekday: collect postings directly from seven applicant tracking systems: Greenhouse, Lever, Ashby, Workable, SmartRecruiters, Rippling and Workday.
  3. Reject postings older than 21 days, outside New York or remote US, or requiring more than 2 years of experience, and read mandatory degree, clearance, citizenship and sponsorship lines from the description.
  4. Deduplicate, keeping the direct ATS record over aggregator copies.
  5. Drop senior titles before any model call, and reuse existing scores for duplicate postings.
  6. Parse and score each remaining posting in one Claude Haiku call. Validate the output against a schema, with exactly one corrective retry.
  7. Classify level fit as fit, stretch or misfit, and rate every posting as official, platform or unverified from its link and text. Unverified postings are never sent.
  8. At 9:00, text the top match over iMessage with reply odds and the best-matching resume. One word acts on it: resume, tailor, skip, applied or next.
  9. Every night, train a ranker on local embeddings, past actions and recruiter-style comparisons kept only when both orders agree. It stays in shadow mode until it beats the current score seven nights in a row.

A4Cost controls

The daily search runs on a Claude subscription through a locked-down Claude Code CLI with no tools, hooks or saved sessions. Backlog scoring uses the Message Batches API at half the standard price, and prompt caching reduces the cost of repeated instructions.

The ranker, embeddings and Gmail classification run locally with no model calls.

Reviewer feedback can move a ranking by at most 5 points, so feedback refines results without overriding the scoring.

B1Human oversight

Sourcer never applies on its own. Every application starts with a one-word reply, and the operator marks it applied.

Tailoring writes only from an evidence bank of approved facts. Facts mined from commit history stay drafts until the operator approves them, and every number or tool in a bullet must appear in the evidence it cites. When a posting asks for a skill with no evidence, Sourcer asks once and saves the answer.

B2Testing and evaluation

CI enforces a 90% test coverage threshold alongside ruff and mypy. A labelled set of postings tests parsing and scoring. The ranker is split by time, so it is always tested on postings newer than anything it trained on. Ten architecture decision records document the design tradeoffs.

B3Scope and status

Runs every weekday for a single operator, with the code and data kept in private repositories. Each application records the exact resume sent and a snapshot of the posting. Follow-ups arrive at day 7 and 14, and Gmail replies mark it interview, assessment or rejection. After 21 quiet days it is marked ghosted.

A1Overview

A relationship-management app that tracks contacts, scores which relationships are drifting, and texts its user first in iMessage: briefs before meetings, follow-ups after events, and nudges timed by a relationship decay model.

4
relationship signals time each nudge
2 a day
maximum check-ins, never in quiet hours
0.906
ROC-AUC of the decay model behind check-in timing

A2The problem

Professional contacts lapse because follow-ups depend on remembering to open a separate app at the right moment.

A3Rekindle in iMessage

Rekindle has its own iMessage number. A user texts it, links their phone once through a one-use, fifteen-minute link, and from then on talks to the agent like any contact.

  1. Each text is queued and answered by a bounded tool loop that can look up who is drifting, find a contact, read their details, check upcoming events, save a note, and pause check-ins.
  2. Rekindle also texts first: a brief 10 to 90 minutes before a meeting with saved contacts, a follow-up within a day of an event where the user met people, and a nudge when a relationship needs attention.
  3. Check-ins skip quiet hours, cap at 2 a day, go out in the hour the user usually texts, and back off when they go unanswered.
  4. Drafts arrive on their own lines, ready to copy and send.
  5. The model is one setting: Claude or any Messages API compatible model can run the agent.

A4When to check in

Every contact gets one attention score from four signals: the decay model's risk that the relationship is going quiet, silence past the pair's own rhythm so weekly friends and quarterly mentors differ, a dip in tone blended across channels, and new connections not yet followed up. Nothing fires within 7 days of contact. Decay risk is rescored daily before check-ins are planned, and the agent's answers about who is drifting use the same scores it texts from.

B1Human oversight

Rekindle texts only its user. Every message it sends goes back to the user's own linked thread, and drafts for contacts are written to copy, so the user always sends. Check-ins pause with a single text. The webhook verifies every signature and never logs message text, and conversation history is purged after 14 days.

B2The product

The product includes the web app, the iMessage agent, a macOS companion, a Chrome extension for LinkedIn, Gmail, Google Calendar and Slack sync, searchable context memory, and a relationship decay model that scored ROC-AUC 0.906 on a held-out test of 112,000 snapshots. The model rescores every linked user daily and feeds check-in timing.

Per-writer tone calibration is applied only when it predicts next-day conversation continuation at least as well as raw tone scores: within 0.01 AUC, with at least 50 examples. Review actions tune the context model's acceptance threshold within 0.70 to 0.95.

B3Scope and status

The iMessage agent is in active development. Turns are claimed once, a crashed turn is reclaimed after two minutes, and failures retry up to three times. A free end-to-end dry run starts an isolated stack, applies every migration, and plays a full scenario against a mock iMessage provider and a scripted model: invite, link, question, meeting brief, nudge, draft, pause. The sample thread on this page uses fictional names.

A1Overview

A policy evidence app for team knowledge bases. It returns the exact approved passage behind every answer, abstains with an explanation when no approved policy covers the question, and flags conflicting policies until an administrator sets precedence.

10/10
unanswerable test questions correctly refused
85
automated backend tests
8
end-to-end browser workflows

A2The problem

When policies span many documents and versions, an answer is only useful if the reader can see which source it came from and whether that source is current.

A3How it works

  1. Uploads are validated, stored and registered as a new document version with an ingestion job.
  2. Workers claim jobs using Postgres row locks with a 60-second lease; a late worker cannot overwrite a newer result.
  3. Text is split into paragraph passages under their heading path, at most 1,200 characters and never broken mid-sentence, and optionally embedded. A new version goes live only after ingestion succeeds, so a failed upload leaves the previous version searchable.
  4. Each query first verifies workspace membership. Workspace isolation is enforced twice: in application checks and in PostgreSQL row-level security.
  5. Search defaults to Postgres full-text. Optional semantic search uses MiniLM embeddings in pgvector, combined with keyword results through reciprocal rank fusion.
  6. Evidence is capped at 8,000 bytes. A relevance gate abstains when the best passage covers less than 40% of the question's terms, and rule-based checks flag policies that disagree. Answers must quote exact retrieved text, and abstentions must state what is missing.

A4Retrieval evaluation

Across 28 labeled development questions, keyword search scored 0.96 recall in the top five results. Hybrid semantic search was compared using MRR, nDCG and a paired randomization test and showed no significant difference (p = 0.19).

That makes fast keyword search the default, with semantic search available as an option.

B1Human oversight

Users see the source passage alongside every answer and can open it in its full section. Where the documents provide no support, the system abstains rather than guessing.

Users can send unresolved questions to a review queue. An administrator answers with cited passages and publishes the answer for reuse, and the answer reopens automatically when the cited policy text changes.

B2Testing and evaluation

85 automated backend tests cover document handling, access control, workspace isolation, review workflows, conflict rules and prompt injection through uploaded documents, with eight end-to-end browser workflows run in CI.

B3Scope and status

The default mode returns approved passages word for word. An optional Claude generator must return schema-valid answers in which every claim cites an exact quote. The policies shown on this page are synthetic.

A1Overview

A LangGraph pipeline that extracts transactions from bank statement PDFs, verifies that the totals reconcile, sends a tool-using repair agent to find and fix the cause when they do not, and routes unresolved statements to human review before Excel export.

142
automated tests
11
replayed test statements
260
transaction volume fixture

A2The problem

Manual statement entry is slow, and a model reading a PDF can misread a single digit with full confidence. In financial data, an incorrect value does more harm than a missing one.

A3How it works

  1. Validate the file. Confirm it is a text PDF.
  2. Extract text with pdfplumber and identify the statement format.
  3. Extract fields into a typed schema with a lower-cost Claude model, allowing up to 2 validation attempts.
  4. Verify that the opening balance plus all transactions equals the closing balance exactly, to the cent, that dates fall inside the statement period, and that the account holder and account number appear in the document text.
  5. If the totals do not reconcile, a repair agent searches the statement for the cause and fixes it, citing the line behind each edit. Every amount, date and description it enters must be printed on that line, and the checks, not the agent, decide whether the fix worked.
  6. Finalize and export to Excel.

A4Human oversight

The repair agent cannot touch the account holder or account number, and a statement that fails the identity check skips the agent entirely. It cannot finish while any check still fails, and it removes a row only with proof from the document. Whatever it cannot fix waits for a person in an optional SQLite review queue, which records every correction, agent edit and approval, and prevents concurrent reviewers from overwriting each other.

B1Export safety

The Excel export writes every value as a text cell, so a malicious transaction description cannot execute as a formula when the file is opened. Results are saved per file by SHA-256 fingerprint, so a crash or a rerun only processes the files that did not finish.

B2Testing and evaluation

142 automated tests and 11 replayed synthetic statement fixtures run in CI with no API key, including a scanned PDF that is correctly rejected and a 260-transaction fixture for volume. Each repair agent tool is tested on its own, and a full run fixes a fee printed outside the transaction table.

B3Scope and status

Built on synthetic statements. It recreates the extraction workflow I built at Ardinall, with no client data or code.
